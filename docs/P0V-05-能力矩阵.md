## 2. 关键设计：能力从哪来（CLAUDE.md 红线 #2）

**能力来自打开后的 Readium `Publication`，不是文件扩展名，也不是 `Book.format`（当前是未填充的死字段）。**

- 格式探测：`Publication.conformsTo(Publication.Profile.EPUB/PDF)`（`Publication` 无 `format` 字段，`conformsTo` 是规范 API，已用 `javap` 读 readium-shared-3.3.0 classes.jar 坐实）。
- 搜索探针：`publication.isSearchable`（`org.readium.r2.shared.publication.services.search`，底层 `findService(SearchService::class) != null`）。
- 适配器：`Publication.toReaderCapabilities()`（`:reader:readium`）把上述探测结果映射为引擎无关的 `ReaderCapabilities`（`:core:model`）。Readium 知识内聚在 readium 模块，`:app` 只调扩展。

**TXT 的天然正确性**：`OpenTxtPublicationUseCase`（P0V-04）把 TXT 转标准 EPUB 后走 `retrieve(..., MediaType.EPUB) → publicationOpener.open`，产出的 Publication `conformsTo(EPUB)=true` → 能力天然等同 EPUB。**能力层完全不需要、也不应该知道原文件是 `.txt`**——这正是红线 #2「不按扩展名承诺能力」的体现。

**`.txt` 打开层分流不算违规**：`ReaderViewModel.openPublication()` 里 `filePath.endsWith(".txt")` 的分流在**打开层**（决定用哪个 use case 把文件变成 Publication——TXT 必须先转 EPUB 才能喂 Readium，是物理前置），不是**能力层**。打开成功后能力 100% 由 `Publication.toReaderCapabilities()` 推导，扩展名从不参与能力判断。红线 #2 针对的是「按扩展名给用户展示按钮」，打开层分流对用户不可见。

**PDF 的 `forPdf()`**：标 spec 意图矩阵（浏览/搜索/书签，无批注），供单测与 V1 兜底。MVP 运行时**永不产生 PDF 能力**（`ReadiumFacade` 的 `DefaultPublicationParser(pdfFactory=null)`，PDF 整体降级 V1）；V1 真开 PDF 时走运行时 `toReaderCapabilities()` 以 `isSearchable` 实测，UI 只看运行时结果。design.md:130「未验证则隐藏」由「MVP 不开 PDF + V1 按 isSearchable 实测」双重保证。

## 3. UI gating 规则（供 Phase 1 严格执行）

`ReaderCapabilities` 的每个字段对应一个 UI 入口；能力为 `false` 时入口**不渲染**（REL-02：能力矩阵与 UI 完全一致，不出现不可用按钮）。

| READ 能力 | UI 入口（Phase 1 将建） | 能力字段 | `false` 时处理 |
| --- | --- | --- | --- |
| READ-05 书内搜索 | 顶栏搜索图标 + 结果列表 | `canSearch` | 不渲染搜索入口 |
| READ-02 目录 / 章节跳转 | 顶栏目录图标 + TOC 面板 | `canToc` | 不渲染目录入口 |
| READ-06 书签 | 顶栏书签图标 + 书签列表 | `canBookmark` | 不渲染书签入口 |
| READ-07 高亮 | 长按 ActionMode「高亮」+ 底栏高亮计数/清 | `canHighlight` | ActionMode 不加菜单项 + 底栏高亮组隐藏 |
| READ-07 笔记 | ActionMode「笔记」+ 笔记面板 | `canAnnotate` | 菜单项 / 面板不渲染 |
| READ-07 复制 / 分享 | ActionMode「复制」「分享」 | `canCopyShare` | 菜单项不加 |
| READ-10 TTS | 顶栏 TTS 图标 + 播放控制 | `canTts` | 不渲染 TTS 入口 |
| READ-01 位置恢复 | （隐式，无入口） | `canRestorePosition` | `false` 时弹「无法恢复位置」提示，不崩溃 |

**P0V-05 已落地的 gating 钩子**（当前 UI 仅有高亮入口，搜索/目录/书签/笔记/TTS 是 Phase 1 的 READ-02/05/06/07/10，尚未建）：

- `ReaderFragment.onCreateActionMode`：`if (viewModel.capabilities.value.canHighlight)` 才加「高亮」菜单项。
- `ReaderScreen.ReaderBottomBar`：底栏高亮计数/清除组包进 `if (canHighlight)`。

MVP 运行时只产生 EPUB（含 TXT-转-EPUB）能力，`canHighlight` 恒 `true`，故 EPUB/TXT 路径行为不变；上述钩子在 V1 打开 PDF（`canHighlight=false`）时自动生效。

## 4. 模型归属决策

`ReaderCapabilities` 当前放 `:core:model`（与 `Book` 同层），**未新建 `:core:reader-api`**。理由：CLAUDE.md「不要随手拆几十个 Gradle 模块」；P0V-05 只需这一个类型，design.md:234 同模块的 `ReaderSession/ReaderLocation/ReaderPreferences` 当前一个都不存在，为单类型开模块是 YAGNI。Phase 1 出现第二个引擎/navigator 抽象时，再把四个类型一起搬进 `:core:reader-api`，搬一个 data class 成本极低。

## 5. 测试覆盖（design.md:348 要求单测覆盖能力矩阵）

`:core:model:testDebugUnitTest` 的 `ReaderCapabilitiesTest` 断言：

- `forEpub()` 全字段 `true`（EPUB 全能力）。
- `forPdf()`：浏览/搜索/书签类 `true`，高亮/笔记/复制分享/TTS `false`（对应 issue #823）。
- `from(_, isSearchable)` 搜索探针对 EPUB/PDF 均生效。
- `from(EPUB, true) == forEpub()`：证明 TXT 走 EPUB Publication 后能力等同 EPUB，无需按扩展名单独算。
- `forEpub()` 与 `forPdf()` 批注类字段严格不同（防回归）。

`Publication.toReaderCapabilities()` 适配器仅 3 行、真实 `Publication` 构造重（需 Manifest+Container，纯单测难），省略其独立测试，覆盖集中在 `:core:model`（与既有「LocatorJsonTest 因 android.net.Uri stub 跑不了被移除」同源决策）。
